# Data contracts and progression integrity

The examples below remain illustrative designs. The runtime schemas listed in the next section load through the vanilla datapack reload system and validate item registries, career IDs, quantities, prices, XP and shared demand. Accepted terms and settlement targets are snapshotted in the durable journal; see [economy integration](economy-integration.md).

## Implemented runtime schemas (Core, `schema_version` required)

All are datapack resources under `data/underground_city/`, loaded atomically on reload; invalid data fails the reload instead of partially applying.

| Resource | Schema | Fields and validation |
| --- | --- | --- |
| `work_orders/*.json` | 1, 2 and 3 | title <= 80 chars, `career` in the four careers, `level` 1-30, credits/xp 1-1000, `capacity` 1-16, `refill_ticks` 1200-72000. Schema 1: one `item`+`count` (1-64). Schema 2: `requirements` (1-4 unique registered, non-air items), optional `foreign_visits` 0-2. Schema 3 adds `legality` (`legal`/`underground`), `requires_skill`, `buyer` (a `buyers/` id; the delivery must happen in that buyer's city), `min_trust`, `trust_gain`, `requires_mod` (the order is **skipped, not an error,** when that mod is absent), `rewards` (item, count, optional `nbt`) and per-requirement `gun_ids` (a plain factory gun whose `GunId` is listed; named, enchanted or attachment-modified guns never qualify). At most 64 orders. Accepted terms are snapshotted; pre-schema-3 saved snapshots still load |
| `skill_trees/<career>.json` | 1 | one file per career, named after it; nodes with `id` `<career>.<name>`, `branch` (core/legal/underground/utility), `cost`, `min_level`, `requires`, `effects` (`inspection_modifier` >= -0.25 per node and >= -0.35 per tree, `exchange_discount` <= 0.10, `licences`). Acyclic; an underground node must descend from a legal node; the whole tree is affordable at level 30 |
| `contraband/*.json` | 1 | a `category` and `entries` matching by item registry id, optionally an NBT string key (`nbt_key`) with `values`, `contains` or a catch-all; a specific entry beats a catch-all |
| `city_laws/<city>.json` | 1 | per-category status (`legal`/`permit`/`prohibited`), `fines`, `inspection` chances by gate risk plus `heat_step` and `max`, `witness_chance`, one-line `summary` |
| `buyers/*.json` | 1 | `title`, `city`, `legality`, `blurb`; trust is per player and capped at 5 |
| `checkpoints/*.json` | 1 | generated from the corridor blueprint: `jurisdiction`, `dimension`, `x`, `z`, `radius` (48), `risk`, `route`; coordinates are data produced by the world plan, never Java |
| `exceptional_loot/*.json` | 1 | a `policy` (property policy id), a one-time `chance`, weighted `entries` (item, optional `nbt`, `count`, `requires_mod`); entries for absent mods are skipped |
| `districts/*.json` | 1 | operator-built lots: `ops` (`fill`, `block`, `terminal`, `safe`, `secure_terminal`, `clerk`, `npc`) in coordinates relative to the operator's origin; at most 400 operations, 64 blocks per axis, 40,000 blocks, 16 citizens. An operation may carry `requires_mod` (skipped when that mod is absent, never an error). A district may be `repeatable` (one copy per place, for example a checkpoint post). An `npc` operation names a `role` (`registrar`, `employer`, `resident`, `guard`), a unique `name` (<= 40 characters), a vanilla villager `profession`, up to 8 `lines` of <= 180 characters, and for an employer a `career` and the `terminal` it is bound to; the file is generated by `scripts/generate_district.py` |
| `regional_stock/*.json` | 1 | `city`, registered non-air `item`, `unit_price` 1-10000, `initial` <= `capacity` <= 256, `units_per_interval` 1-64, `interval_ticks` 1200-720000, `max_order` 1-64; at most 64 lines |
| `regions/*.json` | 1 | `id` (one of the three cities), `dimension`, `center_chunk` [x,z], `radius_blocks` 16-4096; generated from the world blueprint; at most 16 |
| `property_policies/*.json` | 1 | `capacity` 1-9, `initial_stock` <= capacity, `interval_ticks`, `items_per_interval` 1-4, `lockpicks` 1-8, `loot_table`; at most 32 |
| `underground_city_items.json` (classpath) | 1 | generated list of the original item IDs, kind and stack size |

Generated files are produced from [regional-content.json](../../content/gameplay/regional-content.json), [restock-policies.json](../../content/property/restock-policies.json), [loot-tables.json](../../content/property/loot-tables.json) and [cities.json](../../content/region-blueprints/cities.json) by `scripts/generate_regional_content.py`; edit the sources, never the output.

## Rules

Use stable namespaced IDs and explicit `schema_version`. Separate item names, display language, world coordinates and gameplay IDs. Track external registry aliases and migrations. Persist currency as integer units, not floats.

### Example city
```json
{
  "schema_version": 1,
  "id": "underground_city:valewood",
  "spawn_anchor": "underground_city:valewood_registration",
  "region_id": "underground_city:valewood_region",
  "treasury_policy": "underground_city:citizen_starter"
}
```

### Example career
```json
{
  "schema_version": 1,
  "id": "underground_city:farmer",
  "max_level": 30,
  "branches": ["cultivation", "vintner", "agribusiness"],
  "xp_events": ["contract_completed", "new_production"]
}
```

### Example research unlock
```json
{
  "schema_version": 1,
  "id": "underground_city:training_part",
  "career_id": "underground_city:gunsmith",
  "min_level": 3,
  "required_skill_ids": ["underground_city:component_basics"],
  "workstation_id": "underground_city:starter_workbench",
  "reward_id": "underground_city:mechanical_part"
}
```

These example IDs are not confirmed Minecraft items or working recipes.

## Content integrity tests to implement

Validate schemas, unique IDs, missing dependencies, circular prerequisites, unobtainable recipe inputs, mandatory-story reachability for two players, item-registry availability, zero/negative prices and duplicate rewards. Every contract, NPC, crime, city and loot record needs a stable identifier, defined source of truth and migration strategy.
